Problema 02 / 20

El problema

Cuando el modelo cambia, todo lo demás se reescribe a mano.

🗣 Qué decir
  • El ITC desarrolla, con el Jardín Botánico, aplicaciones de gestión de datos botánicos. Su modelo de datos no es estable: crece con la investigación.
  • Cada cambio se propaga en cascada: backend (modelos, validación, endpoints), comunicación (contratos, tipos) y frontend (formularios, tablas, vistas).
  • Casi todo ese código se escribe a mano y queda acoplado a un dominio.
  • El resultado es caro de mantener y difícil de reutilizar.
🔑 Claves & aclaraciones
  • Señalar el diagrama de cascada en la diapositiva: Modelo → Backend → Comunicación → Frontend, todo «a mano».
  • Tres capas afectadas = tres oportunidades de error y repetición.
→ ¿Cuál es la propuesta para resolverlo?
Problema 03 / 20

La propuesta

El modelo de datos como única fuente de verdad.

🗣 Qué decir
  • El desarrollador escribe solo el modelo ORM en SQLAlchemy.
  • El framework deriva un JSON Schema enriquecido con pistas de presentación.
  • Ese esquema viaja por un contrato de comunicación uniforme.
  • En el otro extremo se genera el formulario, sin escribir HTML específico de cada entidad.
  • Son dos piezas: uniback (FastAPI + PostgreSQL) y ngt-gui (Angular). Un cambio en el modelo se propaga solo.
🔑 Claves & aclaraciones
  • Cadena: Modelo ORM → Esquema enriquecido (JSON Schema + x-*) → Contrato uniforme (content · count · issues) → Formulario (<ngt-dynamic-form>).
  • Recalcar que el front nunca necesita conocer la forma concreta de una entidad.

Diseño 07 / 20

Arquitectura general

Dos sistemas y un contrato como única superficie de acoplamiento.

🗣 Qué decir
  • Izquierda — uniback: modelo SQLAlchemy → Pydantic con pistas x-* → JSON Schema enriquecido.
  • Centro — Contrato HTTP: toda respuesta viaja en { content, count, issues }. Tres endpoints clave: esquema individual, bundle y descubrimiento.
  • Derecha — ngt-gui: EntityClient pide el esquema, schemaToFormly() lo traduce, <ngt-dynamic-form> lo renderiza.
  • El frontend nunca necesita conocer la forma concreta de una entidad.
🔑 Claves & aclaraciones
  • Endpoints: GET /<e>/schema.json · GET /api/sys/schemas [ETag] · GET /api/sys/entities.
  • Envoltorio: { content, count, issues } — éxito y error, mismo formato.
  • Esta es la diapositiva-resumen: si me pierdo, vuelvo a este flujo.
→ El corazón del modelo de datos.
Diseño 08 / 20

Núcleo polimórfico

Un núcleo que trata igual lo que es distinto.

🗣 Qué decir
  • Toda entidad hereda de FunctionalObject, asociada a un ObjectType con código numérico.
  • Anotaciones, permisos (ACL) y colecciones apuntan a «cualquier objeto funcional» sin conocer su clase concreta.
  • La autorización usa el mismo patrón: Identity y Role heredan de Authorizable.
  • Consecuencia práctica: Plant (un plugin) hereda todo —anotaciones, permisos, colecciones— sin que el núcleo sepa que existe.
  • Modelo ampliado del ITC, al que añadí versionado con SQLAlchemy-Continuum.
🔑 Claves & aclaraciones
  • Señalar el diagrama: ObjectType → FunctionalObject → Collection / Screen / Plant (plugin, borde discontinuo).
  • Cuando la clase es raíz de jerarquía, el esquema emite oneOf + x-discriminator.
  • Conecta con el Incremento 4 (bundle).
→ Cómo entra el dominio sin tocar el núcleo: plugins.
Diseño 09 / 20

Plugins y micronúcleo

El dominio entra desde fuera: plugins sobre un micronúcleo.

🗣 Qué decir
  • Un plugin hereda de UnibackPlugin y sobreescribe solo los hooks que necesita.
  • Ejemplo — plugin de plantas: declara sus modelos, expone su CRUD con una fábrica y aporta un widget de mapa. Nada más.
  • Refactoricé el backend hacia un micronúcleo: cada dominio (auth, ficheros, anotaciones, especies) es un plugin de serie.
  • Despliegue multinodo: misma imagen Docker, UNIBACK_NODE_TYPE decide qué plugins sirve, Traefik enruta por prefijo. Un nodo nuevo se añade en caliente.
🔑 Claves & aclaraciones
  • Hooks: get_model_modules, get_routers, get_field_widgets.
  • Materializa el requisito de reutilización: el núcleo no acopla lógica de dominio.
  • Diagrama derecho: nodos core · auth · species · files · annotations · assistant + seedbeds (en caliente).

Desarrollo 11 / 20

Incremento 2 · Contrato

Una sola forma para cualquier respuesta.

🗣 Qué decir
  • El contrato es universal: toda respuesta tiene la misma forma — content, count, issues.
  • También los errores: manejadores globales + catálogo de siete códigos estándar. El frontend nunca recibe dos formas distintas de fallo.
  • Fábricas CRUD generalizadas: seis endpoints por entidad, de ≈ 20 a 61 entidades.
  • Descubrimiento: el frontend pregunta qué entidades existen; no las lleva escritas.
  • Capa aditiva: el servicio heredado sigue funcionando sin tocarlo.
🔑 Claves & aclaraciones
  • Señalar los dos bloques de código: respuesta de éxito (borde verde) vs. error de validación (borde naranja).
  • Convención: GET lista · GET /{id} · POST · PUT · DELETE · GET /schema.json.
  • Si preguntan: VALIDATION_ERROR lleva location (viene de Pydantic).

Desarrollo · ⭐ principal aportación 12 / 20

Incremento 3 · Formularios

Del esquema al formulario, sin escribir HTML.

🗣 Qué decir
  • Backend: amplié la conversión SQLAlchemy → Pydantic para inyectar una pista de presentación por columna: Boolean→checkbox, DateTime→datepicker, Enum→select, String largo→textarea, FK→select con carga diferida.
  • Son valores por defecto: lo que el desarrollador declare a mano siempre gana. Viajan dentro del esquema → sobreviven al cacheo.
  • Frontend: schemaToFormly es un conversor puro que traduce el esquema a Formly, con validadores y condiciones de visibilidad.
  • El resultado: una etiqueta y la ruta. El componente descubre, pide, monta, valida y envía.
🔑 Claves & aclaraciones
  • Señalar la tabla izquierda (columna → pista) y el código derecho: <ngt-dynamic-form entityPath="/roles">.
  • «La heurística propone; el desarrollador siempre puede sobrescribirla.»
  • Esta es la diapositiva que demuestra la tesis central.
→ Formalizar la extracción: el bundle.
Desarrollo 13 / 20

Incremento 4 · Esquemas

Todos los esquemas, en un bundle versionado.

🗣 Qué decir
  • Cada fábrica CRUD registra su entidad en un registro global; se construye un bundle: un único documento con todos los esquemas enriquecidos.
  • Su versión = ETag: si nada ha cambiado, el servidor responde 304.
  • Polimorfismo: las subclases viajan como oneOf con su discriminador.
  • Relaciones del ORM reflejadas en x-relationships.
  • Todo es determinista: mismo modelo, misma versión.
🔑 Claves & aclaraciones
  • Señalar el bloque de código con el JSON del bundle: version, entities, oneOf, x-discriminator, x-relationships.
  • Valor extra: un script externo puede pedir el bundle y generar tipos TypeScript, validadores o documentación.
  • Decisión: variantes incrustadas (no $ref) → bundle autocontenido.
